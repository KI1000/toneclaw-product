# ToneClaw 业务架构闭环

> 记录时间：2026-10-03 20:15:20 CST
> 状态：当前业务架构决策底稿
> 文档定位：本文件是 ToneClaw 业务架构的仓库内 SSOT。
> 结论：ToneClaw 先定义统一卖家经营闭环；各跨境平台通过 Adapter 映射到这套闭环，而不是为每个平台各做一套业务系统。

## 1. 核心定位

ToneClaw 的定位是面向跨境电商卖家的 AI 经营产品，不是 DSH 桌面壳，也不是单一平台的 API 工具。

用户可见产品是 ToneClaw。
DSH / DeepSeek Harness 是内嵌引擎和 runtime，不作为产品身份暴露给卖家。
飞书只是可选通知和控制渠道，不进入核心业务架构主链路。

第一版服务对象以一人 OPC 跨境卖家为主，优先跑通一个平台的完整经营闭环。

## 2. 核心原则

```text
一个平台接入 = 一个可运营的卖家闭环
```

但这句原则的实现方式不是：

```text
ToneClaw-Temu 业务系统
ToneClaw-TikTok 业务系统
ToneClaw-Amazon 业务系统
```

而是：

```text
ToneClaw 统一卖家经营闭环
        ↑
    平台适配层
        ↑
Temu / TikTok / Amazon / 其他平台
```

也就是说：

1. 平台接入不能只做“API 打通”或“数据同步”。
2. 每个平台接入完成后，必须支持该平台卖家的一段完整经营链路。
3. 闭环属于 ToneClaw 核心域；平台只是能力来源、约束来源和业务模式差异来源。
4. 可以有人工环节，但不能有系统黑洞。

## 3. 统一卖家经营闭环

ToneClaw 的核心业务闭环是：

```text
店铺接入 / 授权
→ 货盘 / 选品
→ 商品资料准备
→ 商品图 / Listing / 类目 / 价格 / 库存
→ 上架 / 审核 / 在售
→ 订单 / 备货单 / 发货单
→ 履约 / 发货 / 物流 / 时效
→ 售后 / 退款 / 评价 / 异常
→ 结算 / 佣金 / 费用 / 回款
→ 利润核算
→ 经营复盘
→ 反哺选品 / 补货 / 定价 / 下架
```

其中真正的经营闭环终点不是“发货完成”，而是“利润和复盘结果能回流到下一次经营决策”。

```text
选品 → 上架 → 出单 → 履约 → 回款 → 利润 → 复盘 → 再选品
```

## 4. 统一对象模型

平台适配层最终应把平台数据映射到以下核心对象：

| 核心对象 | 说明 |
|---|---|
| Store | 卖家店铺、授权状态、平台身份、经营模式 |
| Product | 从货盘 / 选品结果转化出的卖家经营商品 |
| Supplier | 供应商、货源资质、起订量、供货能力 |
| SourcingItem | 平台无关的统一货盘商品 / 供应商 / 选品候选 |
| SelectionDecision | 平台无关的选品判断：候选、通过、拒绝、观察 |
| PlatformFitAssessment | 某个平台对商品的适配评估：类目、合规、价格带、履约、竞争度 |
| Listing | 平台侧商品链接、标题、图、类目、价格、库存 |
| Order | 订单、备货单、发货单、履约状态 |
| Fulfillment | 发货、物流、时效、异常 |
| AfterSale | 退款、退货、差评、纠纷 |
| Settlement | 平台费用、佣金、回款、结算周期 |
| CostProfit | 采购成本、物流成本、平台费用、汇率、利润 |
| Insight | 经营日报、异常告警、复盘建议、补货 / 调价 / 下架建议 |

平台数据可以有差异，但进入 ToneClaw 后必须归一到这些业务对象上。

统一货盘是平台无关能力，面向所有平台店铺卖家。`SourcingItem` 不归属于单一 Marketplace；Temu、TikTok Shop、Amazon、Shopee、AliExpress 或独立站后续都可以复用同一货盘。Temu 只是第一个消费方。

选品同样是平台无关核心能力。`SelectionDecision` 判断一个货盘商品是否值得进入卖家经营商品池，不归属于 Temu。平台差异放在 `PlatformFitAssessment` 中，例如 Temu 类目、资质、禁售规则、价格带、履约方式和竞争度。P0 只实现 Temu 平台适配评估，但选品核心模型必须支持后续平台复用。

## 5. 系统分层

```text
入口层
├── ToneClaw 桌面端
├── 飞书：可选通知 / 远程控制渠道
└── 未来 Web / Mobile

ToneClaw 产品层
├── 店铺接入与授权
├── 货盘 / 选品
├── 商品图生成
├── Listing 生成与上架
├── 订单 / 履约 / 售后
├── 结算 / 成本 / 利润
├── 经营日报 / 异常提醒 / 复盘
├── 软件计费
└── Token / AI 用量计费

平台与系统接入层
├── Marketplace Adapter
│   ├── Temu：第一个接入平台
│   ├── TikTok Shop：后续
│   └── Amazon：后续
├── 货盘 / 供应商数据源
└── ERP / WMS：后续接入

DSH 引擎层
├── Session / Agent
├── Tool Runtime
├── Workspace
├── Permission
├── Jobs / Schedule
└── Plugin Composition
```

## 6. 平台接入验收标准

一个平台接入完成，不是以下标准：

```text
能拉店铺
能拉商品
能拉订单
```

而应该是：

```text
卖家能在 ToneClaw 中完成该平台的关键经营链路；
关键对象都有状态；
每个状态都有下一步动作；
异常可以被看到和处理；
成本、费用、回款和利润能回流；
复盘结果能反哺选品、定价、补货和下架。
```

平台接入验收还必须明确：

| 问题 | 结论要求 |
|---|---|
| 接入哪类卖家？ | 全托管 / 半托管 / 市场型 / 本土店等模式必须明确 |
| 闭环从哪开始？ | 例如货盘 / 选品 / 已有商品导入 |
| 闭环到哪结束？ | 例如回款、利润、复盘 |
| 哪些动作自动化？ | 明确低风险自动、中风险建议、高风险人工确认 |
| 哪些动作人工完成？ | 人工动作也要进入系统状态，不允许脱离系统 |
| 平台不支持的能力怎么办？ | 标记为平台限制，不伪装成已完成 |
| 数据如何回流利润？ | 订单、履约、售后、结算、费用必须关联到利润模型 |

## 7. Temu 接入定位

Temu 是第一个 Marketplace 接入对象，不是 ERP。

接入 Temu 前，必须先明确卖家模式：

```text
Temu 全托管
Temu 半托管
Temu 本土店
```

不同模式的闭环不同：

- 全托管：卖家重点在供货、报价、备货、入仓、结算、利润；消费者侧 Listing 和订单运营主要由 Temu 承担。
- 半托管：卖家承担更多商品、库存、订单、履约、售后责任，更接近完整卖家经营闭环。
- 本土店：会额外引入本地库存、本地履约、本土结算和合规差异。

第一阶段应选择一个明确的 Temu 卖家模式，先跑通该模式的可运营闭环；不要同时覆盖所有模式。

## 8. 第一版业务重点

第一版应聚焦一人 OPC 卖家可用的最小经营闭环：

```text
店铺接入
→ 货盘 / 选品
→ 商品图生成
→ Listing 生成
→ Temu 商品上架 / 上架草稿
→ 订单 / 履约状态可见
→ 软件计费
→ Token / AI 用量计费
```

第一版可以不追求全自动，但必须满足：

1. 货盘、选品、商品图、Listing、上架是主链路，不是附属演示功能。
2. 卖家能看到每个商品从候选到在售的状态。
3. 上架相关高风险动作应有确认机制。
4. AI 生成消耗应进入 Token 计费。
5. 软件订阅 / 授权应进入软件计费。
6. Temu 的平台限制要清晰暴露，不能为了演示而隐藏风险。

## 9. ERP / 货盘 / 外部渠道的角色

### ERP

ERP 是卖家内部经营系统，后续接入，不等于销售平台。

ERP 未来主要补充：

- 采购
- 库存
- 仓储
- 发货
- 成本
- 供应链协同

### 货盘

货盘是面向所有平台店铺卖家的统一商品来源池，不是 Temu 专属能力。

它不绑定某一个 Marketplace。Temu、TikTok Shop、Amazon、Shopee、AliExpress 或独立站后续都应复用同一货盘。Temu 只是 P0 的第一个消费平台。

同一个 `SourcingItem` 可以在不同平台生成不同的 `Product` 和 `Listing`。但平台相关的类目映射、合规资质、文案规范、图片规格、价格策略和库存策略，由对应平台适配层处理。

需要区分两个概念：

```text
货盘模型跨平台共享
≠ P0 同时接入多平台店铺
```

P0 仍然只接入 Temu 店铺，但货盘对象模型必须具备跨平台复用能力。

它的作用是进入：

```text
货盘 → 选品 → 商品图 → Listing → 上架
```

货盘不是单纯的表数据，应至少包含选品和上架所需的关键信息，例如商品、规格、图片、价格、起订量、供货能力、类目候选和资质信息。

其中，商品、规格、图片、价格、起订量、供货能力和通用资质属于货盘核心数据；Temu 类目、Temu 属性、Temu 资质校验、Temu 图片规格等属于平台适配映射，不应让货盘核心对象被某一个平台定义。

### 飞书

飞书不是业务重点，只是外部渠道：

- 接收通知；
- 查看经营摘要；
- 远程发起简单指令；
- 接收异常提醒。

飞书不应承担核心业务状态管理，也不应成为产品身份。

## 10. 架构判断标准

后续功能设计必须回答：

1. 这个功能属于统一经营闭环的哪个对象？
2. 它改变哪个对象的状态？
3. 它是平台能力、DSH 能力，还是 ToneClaw 产品能力？
4. 它如何进入利润或复盘？
5. 它是否需要人工确认？
6. 它是否会被计费？
7. 换一个平台后，这个能力的核心模型是否仍然成立？

如果一个问题只在某个平台成立，应放在平台 Adapter；
如果它在多个平台成立，应放进 ToneClaw 核心业务模型。
